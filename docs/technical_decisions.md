## 3. 核心语言与运行平台

### TD-001：核心程序使用Linux C11

状态：已采用。

背景：

项目面向嵌入式Linux应用开发、网络协议解析和DPI相关岗位，需要直接处理原始字节、网络字节序、固定宽度整数、内存生命周期、系统调用和多线程同步。

决定：

核心采集、解析、流聚合和规则检测使用ISO C11，并通过POSIX接口使用Linux能力。

主要理由：

- C能够直接表达字节布局、指针、缓冲区边界和资源生命周期；
- C11提供`stdint.h`、复合字面量、布尔类型和更明确的语言基础；
- libpcap和pthread都提供成熟的C接口；
- C程序运行时依赖较小，适合资源受限的ARM Linux设备；
- 该选择能直接展示嵌入式Linux岗位关注的底层能力。

没有把C++作为核心语言的原因：

C++可以提供RAII、容器和泛型，但第一阶段更需要明确练习内存、错误码和资源所有权。未来Qt上位机仍会使用C++，但不会要求采集和解析核心依赖Qt运行环境。

代价与复审条件：

- C缺少标准容器和自动资源管理，需要自行设计队列、哈希表和清理路径；
- 如果应用层解析器数量显著增加，或者模块扩展成本明显高于收益，可以评估在稳定C接口之外增加C++封装。

### TD-002：开发环境与目标环境分离

状态：开发环境已采用，目标环境待上板验证。

决定：

- 开发主机：x86_64 Ubuntu 24.04 LTS；
- 源码放在Ubuntu原生ext4目录；
- Windows上的VS Code通过Remote-SSH操作Ubuntu；
- 编译、测试、Git和抓包实际都在Ubuntu中执行；
- 最终目标：ARM64 Linux开发板。

主要理由：

- PC上的编译、调试和自动化测试速度更快；
- Linux环境与最终目标系统共享GCC、CMake、POSIX和libpcap生态；
- 先在PC排除业务逻辑错误，再定位ARM架构、驱动和性能差异；
- Ubuntu LTS的软件包、文档和维护周期适合持续开发。

为什么不从第一天只在开发板上写代码：

板端编译速度、存储、调试界面和故障恢复能力都弱于PC。只在板端开发会把协议逻辑问题与硬件环境问题混在一起，降低排查效率。

参考：[Ubuntu发布周期](https://ubuntu.com/about/release-cycle)。

## 4. 构建、测试与工程组织

### TD-003：使用CMake、Ninja和CTest

状态：已采用。

决定：

- CMake描述目标、源码、公开头文件、第三方依赖和编译选项；
- Ninja作为当前开发机的默认构建后端，Make仍可使用；
- Debug和Release使用不同构建目录；
- CTest统一启动C测试程序和Python端到端脚本；
- 导出`compile_commands.json`供VS Code和静态分析工具使用。

主要理由：

- 项目已经包含核心库、命令行程序和多个测试目标，手写单一gcc命令难以维护；
- CMake能够查找libpcap、Python和线程库，并为未来交叉编译提供工具链文件入口；
- Ninja增量构建输出简洁、速度快，但它只是后端，不成为源码的硬依赖；
- CTest按照退出码统一判断不同语言编写的测试是否通过。

为什么不长期维护手写Makefile：

Makefile仍需要理解，但当前项目的重点不是重复维护平台相关的依赖和链接规则。CMake生成Makefile或Ninja规则，能够减少构建配置重复。

参考：[CMake Testing and CTest](https://cmake.org/cmake/help/latest/guide/tutorial/Testing%20and%20CTest.html)。

### TD-012：C单元测试与Python端到端测试分工

状态：已采用。

决定：

- C测试直接调用模块接口，验证边界、错误码、状态和数据结构；
- Python脚本生成确定性PCAP，启动真实命令行程序并检查整体输出；
- CTest负责统一注册和执行。

主要理由：

- C测试离被测函数最近，失败后容易定位具体模块；
- Python更适合创建临时目录、拼装测试文件、启动子进程和匹配输出；
- Python不进入正式程序运行链路，因此不会增加板端部署依赖；
- 端到端测试弥补“所有模块单测通过，但应用连接方式错误”的盲区。

代价：

测试环境比正式运行环境多一个Python依赖。发布构建可以使用`BUILD_TESTING=OFF`关闭测试目标。

## 5. 数据采集与PCAP

### TD-004：使用libpcap，并从离线PCAP开始

状态：已采用。

决定：

正式程序通过libpcap读取原始数据包。第一阶段使用离线PCAP建立可重复验证的分析链路，第二阶段继续通过同一个采集模块接入实时网卡。

当前进展：

- `capture_open_offline()`负责打开离线PCAP；
- `capture_open_live()`负责打开实时网卡，并显式接收快照长度、混杂模式和读取超时；
- 两种输入统一复用链路类型查询、逐包读取、错误查询和关闭接口；
- CLI使用`--interface NAME [--count PACKETS] [--filter EXPRESSION]`运行实时处理循环；省略`--count`时持续运行，提供时使用有限包数上限；
- 实时与离线数据复用同一套协议解析、双向流聚合和输出函数，采集来源差异被限制在应用编排层；
- 提供`--count`时只限制返回应用的包数而不是等待秒数；安装BPF后只统计匹配包，实时模式可以通过`SIGINT`或`SIGTERM`结束，并在关闭句柄前取得libpcap运行统计。

选择libpcap的原因：

- 能直接获得原始数据、时间戳、捕获长度和线路长度；
- 离线和实时抓包使用相近的数据模型，后续迁移成本较低；
- Linux网络分析工具生态成熟，便于与tcpdump和Wireshark交叉验证；
- 不需要自行处理不同平台的底层抓包设备接口。

为什么先做离线PCAP：

- 输入固定，可重复运行；
- 不依赖root权限、网卡状态、实时流量和抓包时机；
- 单元测试与端到端测试可以构造边界报文；
- 同一个文件可以交给本程序、tcpdump和Wireshark对比；
- 协议解析错误与实时采集错误能够分开定位。

为什么不直接解析tcpdump文本：

tcpdump适合人工排障，但文本格式不是稳定的业务API。启动子进程并解析文本会引入管道、进程生命周期、格式变化和错误传递问题。项目运行路径使用libpcap，tcpdump负责抓包和对照，Wireshark负责图形化逐字段验证。

为什么不只使用Wireshark：

Wireshark是成熟分析工具，但项目目标是开发可嵌入业务程序的采集、解析、聚合和异常检测模块，而不是只完成人工查看。自己基于libpcap实现可以继续接入线程、规则、告警和硬件部署。

代价与复审条件：

- libpcap是核心第三方依赖，目标系统必须提供对应头文件和库；
- 高速实时抓包可能出现丢包，接口速率不等于程序可持续处理速率；
- 如果常规libpcap无法满足真实吞吐量，再通过性能数据评估AF_PACKET、TPACKET_V3、AF_XDP或DPDK，而不是提前增加复杂度。

参考：[libpcap项目](https://github.com/the-tcpdump-group/libpcap)、[pcap_open_offline手册](https://www.tcpdump.org/manpages/pcap_open_offline.3pcap.html)。

### TD-020：通过libpcap classic BPF在读取循环前过滤实时流量

状态：已采用。

决定：

采集模块公开`capture_set_filter()`，接收项目自己的不透明`capture_t`、BPF表达式和可选错误缓冲区，不向公开头文件暴露`pcap_t`或`struct bpf_program`。第一版CLI只允许实时模式使用`--filter EXPRESSION`；底层采集接口同时支持离线句柄，以便构造确定性测试。

应用层使用以下顺序：

```text
打开capture句柄
→ 查询并验证链路类型
→ 编译并安装BPF
→ 初始化流表
→ 进入数据包读取循环
```

实现和所有权：

- `pcap_compile()`启用优化，并暂时使用`PCAP_NETMASK_UNKNOWN`；
- 编译成功后调用`pcap_setfilter()`，无论安装成功还是失败都调用`pcap_freecode()`释放临时编译结果；
- 表达式字符串借用自`argv`，应用上下文不复制、不修改，也不负责`free`；
- 已安装过滤器的生命周期由libpcap采集句柄管理，释放临时`bpf_program`不会取消过滤；
- 参数错误返回`EINVAL`，编译或安装失败返回`EIO`并复制libpcap错误；
- 采集层配置失败时不擅自关闭句柄，应用编排层负责组装错误信息并统一调用`capture_close()`。

原因：

- 实时接口包含系统上所有符合链路条件的流量，缺少过滤时，无关TCP流可能先占满有限的`--count`；
- 在协议解析和流聚合前过滤可以减少无关数据进入应用处理链，并让人工演示更可重复；
- 复用libpcap标准过滤语法和编译器，比项目自行解析过滤表达式更可靠，也能与tcpdump使用相近表达式；
- 实时过滤可能由内核或具体捕获后端执行，实际位置依赖平台和libpcap后端，因此不假定所有环境都具有相同卸载行为。

行为影响：

- 不提供`--filter`时，`--count`统计libpcap返回的全部数据包；
- 提供过滤器后，只有匹配包会返回应用、增加计数并进入协议解析和流表；
- classic BPF是包级筛选机制，不等于eBPF应用框架，也不等于需要TCP重组和应用层语义的DPI。

验证：

- 使用离线Ethernet PCAP验证合法表达式安装、非法语法错误、ICMP匹配和TCP排除，不依赖root或真实网卡；
- 冒烟测试覆盖初始化、重新解析、清理、缺失值、空表达式、重复参数和离线组合；
- 在`lo`上使用`--filter "icmp"`和`ping -c 2 127.0.0.1`完成4包人工验收；
- BPF完成后全部15项CTest通过。

代价与复审条件：

- `PCAP_NETMASK_UNKNOWN`不适合依赖真实IPv4网络掩码的广播过滤表达式；
- CLI尚未开放离线PCAP过滤，出现明确需求后可以复用现有采集接口放宽限制；
- libpcap运行统计、周期速率和流表容量指标已经接入；数据模型已经建立五种应用处理结果，下一阶段把分类结果接入单包处理控制流和周期输出。

参考：[pcap_compile手册](https://www.tcpdump.org/manpages/pcap_compile.3pcap.html)、[pcap_setfilter手册](https://www.tcpdump.org/manpages/pcap_setfilter.3pcap.html)、[pcap_freecode手册](https://www.tcpdump.org/manpages/pcap_freecode.3pcap.html)。

### TD-021：使用POSIX信号和pcap_breakloop优雅停止实时采集

状态：已采用。

背景：

终端中的Ctrl+C由Linux TTY子系统转换成发往前台进程组的`SIGINT`。没有自定义处理器时，默认动作会立即终止进程；操作系统会回收内存和文件描述符，但不会替应用输出已经聚合的流、取得抓包统计或执行后续线程和文件的业务收尾。接管信号后，如果处理器只设置停止标志，应用又可能仍阻塞在`pcap_next_ex()`中，无法回到读取循环观察标志。

决定：

- 仅为实时抓包使用`sigaction()`安装`SIGINT`和`SIGTERM`处理器，帮助、版本和离线模式保留默认信号行为；
- 停止标志使用`volatile sig_atomic_t`，处理器不执行`printf()`、内存释放、文件关闭或流表遍历；
- 采集层公开`capture_break_loop()`封装`pcap_breakloop()`，继续隐藏`pcap_t`；
- 应用上下文在读取循环期间临时借用活动`capture_t`，停止请求先设置标志，再请求中断读取；
- 读取循环在调用`capture_next_packet()`前后都检查停止标志，避免已经请求停止后再次阻塞，也避免把信号引起的返回误报成采集错误；
- handler的信号掩码同时包含`SIGINT`和`SIGTERM`，避免两种停止信号嵌套执行；
- 不设置`SA_RESTART`，防止被信号打断的底层读取自动重新开始；
- 保存原来的信号处理方式，并在清理应用上下文前恢复。

涉及的系统边界：

```text
Ctrl+C或kill/systemd
→ Linux内核投递SIGINT或SIGTERM
→ 用户态handler发布停止请求
→ pcap_breakloop请求libpcap结束读取
→ 应用循环恢复控制
→ 关闭capture并输出包统计和流汇总
```

该机制使用Linux内核的信号投递和libpcap的采集中断接口，但不直接控制网卡硬件或驱动。`sigemptyset()`只初始化一个空的`sigset_t`，`sigaddset()`向处理器执行期间的临时屏蔽集合加入信号，真正的处理方式由`sigaction()`注册到进程。

为什么不保留默认Ctrl+C行为：

- 默认`SIGINT`虽然能终止进程，但会跳过读取循环之后的包统计、流汇总和应用清理；
- 操作系统资源回收不能替代输出刷新、统计保存、线程退出和队列排空等业务收尾；
- 开发板上通过systemd或管理脚本运行时还需要处理`SIGTERM`。

为什么不只依赖读取超时：

- libpcap的包缓冲超时不是所有平台上无流量时都必然发生的周期唤醒；
- `pcap_breakloop()`由libpcap文档明确允许在UNIX信号处理器中调用，并能在受支持的Linux实时接口上唤醒阻塞读取；
- 中断接口留在capture模块内，避免应用层依赖第三方原生类型。

验证：

- 使用包含一个数据包的离线PCAP验证提前调用`capture_break_loop()`后读取返回正常结束状态，而不是交付该数据包；
- 在`lo`没有匹配流量时按Ctrl+C，程序能够从阻塞读取返回，输出0包和0条流并正常退出；
- 捕获部分ICMP流量后按Ctrl+C，程序保留已聚合的数据并输出最终流汇总；
- 从另一个终端发送`SIGTERM`时走同一条收尾路径；
- 完成后全部15项CTest通过。

代价与复审条件：

- 当前只有一个静态应用上下文和一个活动采集对象，适合单线程CLI；接入多个采集线程后应重新评估`sigwait()`、专用信号线程、self-pipe、`eventfd`或`signalfd`；
- `active_capture`是普通借用指针，当前依靠单线程生命周期以及处理器安装和恢复顺序保持有效，多线程阶段需要使用正式同步机制；
- Linux实时接口的阻塞唤醒行为取决于libpcap版本和采集后端，开发板验收时需要记录并验证目标机libpcap版本；
- 当前收到停止信号后正常返回成功状态；接入服务管理器后应根据监控和重启策略复审退出码约定；
- `pcap_stats()`已经通过项目自有结构封装，并与应用实际处理包数分开输出；后续多线程阶段仍需重新定义各阶段的应用丢弃计数。

参考：[sigaction手册](https://man7.org/linux/man-pages/man2/sigaction.2.html)、[signal概览](https://man7.org/linux/man-pages/man7/signal.7.html)、[pcap_breakloop手册](https://www.tcpdump.org/manpages/pcap_breakloop.3pcap.html)。

### TD-022：区分捕获后端统计与应用处理计数

状态：已采用。

背景：

`app.c`中的`Total packets`统计应用通过`capture_next_packet()`实际取得并进入处理链的数据包。libpcap的`pcap_stats()`则查询操作系统捕获后端的累计统计，两者处于不同观察层，数值不保证相等。只输出应用包数无法判断抓包缓冲区是否因读取不及时而丢包，只输出`ps_recv`又容易被误解成应用完成处理的数量。

决定：

- 采集模块定义不含第三方类型的`capture_statistics_t`，把`ps_recv`、`ps_drop`和`ps_ifdrop`转换为项目统一的`uint64_t`字段；
- `capture_get_statistics()`只支持实时句柄，离线PCAP没有原运行环境统计，明确返回`ENOTSUP`；
- capture对象在私有实现中记录来源类型，不把该状态和`struct pcap_stat`暴露给上层；
- 统计查询在读取循环结束后、`capture_close()`之前执行；依赖句柄的libpcap错误文本也必须在关闭前复制；
- 统计查询属于辅助可观测性。查询失败时输出不可用说明，但不把已经成功完成的包解析和流聚合改判为失败；
- 终端同时保留`Total packets`和三项捕获后端统计，不使用两者之差推导丢包。

Linux与回环接口语义：

- Linux上的`ps_recv`统计通过捕获过滤器的PF_PACKET事件，并可能包含尚未被应用读取的包；
- 回环通信中的同一个逻辑包会同时以outgoing和incoming形式出现；
- libpcap会抑制交付给应用的loopback outgoing重复副本，但底层统计仍可能已经计算该事件；
- 因此`ping -c 2`产生2个Echo Request和2个Echo Reply时，本项目观察到`Total packets: 4`和`Capture received packets: 8`是合理结果，不表示应用重复处理，也不表示丢失4个包；
- `ps_ifdrop`为0在部分平台上也可能表示不支持该指标，不能无条件解释为接口确定没有丢包。

验证：

- 单元测试覆盖NULL参数、离线句柄`ENOTSUP`和失败不修改输出对象；
- 实时`lo`与ICMP BPF过滤验收成功取得统计，并观察到4个应用包对应8个捕获后端事件；
- 接入周期指标和非阻塞等待后，全部17项CTest通过。

后续：

`pcap_stats()`只提供捕获后端累计值。周期PPS、Mbps、流表占用率和过期数量已经由项目自己的运行指标模块提供；下一阶段仍需为协议解析成功、截断、畸形、不支持、流表拒绝和以后线程队列丢弃建立应用计数。

参考：[pcap_stats手册](https://man7.org/linux/man-pages/man3/pcap_stats.3pcap.html)、[libpcap Linux统计与回环处理实现](https://github.com/the-tcpdump-group/libpcap/blob/master/pcap-linux.c)。

### TD-025：实时周期任务使用非阻塞采集与`poll()`驱动

状态：已采用。

背景：

周期运行指标必须在没有匹配数据包时仍能输出。初版直接依赖`pcap_open_live()`的读取超时和阻塞式`pcap_next_ex()`，但在Linux `lo`完全静默时，第一次报告直到数据包到来后才出现，实际区间达到20.999秒。libpcap的`to_ms`用于抓包缓冲区超时，其生效方式依赖平台和捕获后端，不能当作应用层墙钟定时器。

决定：

- 实时句柄打开并安装BPF后，显式调用`pcap_setnonblock()`进入非阻塞模式；
- capture私有对象保存`pcap_get_selectable_fd()`返回的可选择文件描述符，不向公开接口暴露`pcap_t`；
- 没有可交付数据时，`capture_next_packet()`返回暂时无数据状态，应用再通过项目接口调用`poll()`等待可读或超时；
- `poll()`单次最多等待1秒，使主循环能检查停止请求和约5秒的运行指标期限；
- 报告是否到期仍以`CLOCK_MONOTONIC`及实际经过时间判断，1秒只决定检查粒度，不作为速率计算分母；
- `EINTR`返回主循环重新检查信号停止标志，保持Ctrl+C和SIGTERM的正常清理路径。

为什么不为统计单独创建线程：

- 当前包计数、字节计数、流表和过期数量都由单线程主循环拥有；
- 统计线程若并发读取这些状态，需要原子变量或互斥锁，还要解决一致快照、输出交错、线程停止与`join`顺序；
- 当前没有证据表明单线程计算指标形成瓶颈，为定时输出引入共享状态并发的收益不足；
- 如果以后采集、解析和输出本身因性能数据需要拆成流水线，再统一设计各阶段指标和同步机制更合理。

未采用方案：

- 忙轮询非阻塞句柄：响应快，但接口静默时会持续消耗CPU；
- 固定`sleep()`：实现简单，但睡眠期间不能及时读取包，会增加延迟并可能加剧捕获缓冲区压力；
- 定时信号：handler中不能安全执行`printf`、流表遍历等复杂操作，还会增加信号与采集停止语义的耦合；
- 继续依赖libpcap读取超时：实测已经证明静默时不提供所需的周期唤醒保证。

验证：

- 静默阶段连续得到约5.007至5.008秒的`packets=0`报告；
- 执行`ping -i 0.2 -c 30 127.0.0.1`后，60个应用包分别进入16包和44包两个报告区间；
- 流量结束后报告恢复为零，活动ICMP流仍保留在流表中等待事件时间推进；
- Ctrl+C后正常输出60个应用包、120个捕获后端事件和零drop统计；
- 全部17项CTest通过，且`git diff --check`无空白错误。

代价与复审条件：

- `pcap_get_selectable_fd()`和`poll()`使这一实现带有POSIX/Unix平台边界；若目标捕获后端不提供可选择描述符，需要增加替代等待策略；
- 1秒等待上限带来最多约1秒的周期检查抖动，但速率使用真实区间计算，不影响计数正确性；
- 当前尚未记录空闲和高流量场景的CPU/RSS数值，开发板部署后仍需完成性能验收；
- 当性能测量证明单线程读取或处理成为瓶颈时，再复审线程流水线、队列背压和分阶段丢弃指标。

## 6. 二进制数据与协议解析

### TD-005：边界检查游标、切片和`memcpy`

状态：已采用。

决定：

所有协议字段读取都以`caplen`为边界，通过字节游标执行读取、跳过和切片；原始字节复制使用`memcpy`，不使用字符串复制函数。

主要理由：

- 网络报文是二进制数据，内部允许出现`0x00`，没有字符串终止符；
- `strcpy`、`strlen`等接口无法表达报文长度和截断边界；
- 游标集中维护当前位置和剩余长度，减少每个解析器重复写指针运算；
- `memcpy`避免直接把未对齐地址强制转换为整数指针造成未对齐访问或别名问题；
- 显式的大端读取保证x86与ARM得到相同数值。

代价：

代码比直接强制转换更长，但换取了边界清晰、跨平台和可测试性。

### TD-006：隔离第三方库类型

状态：已采用。

决定：

只有`capture`模块直接包含libpcap头文件。上层使用`capture_t`、`capture_packet_t`和`CAPTURE_LINK_TYPE_ETHERNET`等项目类型，不直接依赖`pcap_t`或`DLT_EN10MB`。

主要理由：

- 限制第三方库影响范围；
- app和协议解析器不需要理解libpcap内部类型；
- 单元测试可以构造项目数据，不必伪造libpcap句柄；
- 未来替换或增加实时采集后端时，上层接口保持稳定。

这里的转换不是重复定义协议，而是在第三方边界上建立项目自己的抽象。

### TD-007：分层协议解析器

状态：已采用。

决定：

Ethernet、IPv4、TCP、UDP和ICMP分别由独立模块解析，通过负载视图逐层传递，不把所有字段读取写进`app.c`。

主要理由：

- 协议天然具有封装层次；
- 每个模块可以独立测试截断、格式错误和不支持状态；
- app只负责调度，不依赖每个字段偏移；
- 后续加入VLAN、IPv6或应用层协议时不会持续扩大单个函数。

## 7. 流量模型、流表与哈希

### TD-008：规范化双向五元组

状态：已采用。

决定：

使用源IPv4、源端口、目标IPv4、目标端口和协议号标识一条流，并对两个端点排序，形成`endpoint_a`和`endpoint_b`。

主要理由：

- 正向包和反向包应聚合到同一条连接记录；
- 规范化后只需要一个流表键；
- 两个方向的包数和字节数仍分别统计，不会丢失方向信息；
- ICMP没有TCP或UDP端口，当前阶段统一使用0端口。

限制：

标准五元组不能区分所有ICMP会话，也不处理NAT前后关联、隧道和IPv6。应用需求扩大后需要扩展键模型。

### TD-009：先用线性流表验证模型，再切换开放寻址哈希流表

状态：已采用。

决定：

第一版使用调用者提供的定长连续数组和线性查找；验证流键、方向、记录生命周期和输出正确后，切换为固定容量开放寻址哈希流表。哈希冲突使用线性探测解决，槽位使用`EMPTY`、`OCCUPIED`和`DELETED`三种状态。

为什么不一开始就写哈希表：

- 线性数组容易理解和调试；
- 第一版最多256条流，足够验证业务链；
- 先确定`flow_key_equal`和流记录模型，再处理冲突、负载因子、扩容和删除；
- 当结果错误时，可以先排除复杂的槽位状态。

为什么最终需要哈希：

线性查找平均和最坏复杂度都是`O(n)`；流数量增长后，每个数据包都扫描大量记录。哈希表通过`hash % capacity`定位候选槽位，平均查找接近`O(1)`。

为什么当前仍然固定容量：

- 固定容量可以明确内存上限，符合嵌入式程序对资源可预测性的要求；
- 调用者提供槽位数组，流表不需要决定使用栈、静态区还是堆；
- 当前容量为256，现阶段重点是验证冲突、删除和业务链正确性；
- 后续先测量流数量、负载因子和探测长度，再决定采用重建、动态扩容还是保持固定上限。

代价：

哈希表必须正确处理冲突、数组回绕、空槽和删除标记。删除后的槽位不能立即变成`EMPTY`，否则会中断其他冲突记录的查找；命中候选槽位后仍必须使用`flow_key_equal`确认完整流键。当前版本尚未实现负载因子控制和动态扩容，容量耗尽时返回`ENOSPC`。

### TD-010：使用FNV-1a 64位哈希

状态：已采用并接入正式流表定位。

决定：

对规范化流键的13个业务字节使用FNV-1a 64位算法。IPv4地址和端口按固定大端字节序参与计算，不直接哈希结构体内存。

选择FNV-1a的原因：

- 实现短小，只需要逐字节异或和乘法；
- 不需要动态内存、查表或第三方库；
- 适合长度固定且很短的五元组键；
- 64位结果提供足够大的哈希空间；
- 算法确定，便于使用固定测试向量验证x86和ARM一致性；
- RFC 9923将FNV描述为快速、分布良好的非加密哈希，并给出FNV-1a流程和参考实现。

为什么不用结构体原始内存：

`flow_key_t`可能含有编译器填充字节，且多字节整数在不同CPU上的内存字节序可能不同。逐字段按固定字节序处理可以得到跨平台稳定结果。

为什么没有选择其他算法：

- 简单累加或djb2容易实现，但字段混合和正式参考不足；
- MurmurHash和xxHash具有更强的吞吐性能，但实现和依赖更复杂，当前13字节键没有证明需要它们；
- SipHash能够抵抗攻击者构造大量冲突，但需要随机密钥且计算成本更高。

安全边界与复审条件：

FNV-1a不是加密算法，也不抵抗恶意碰撞。如果程序以后直接暴露在不可信高速网络中，并观察到冲突攻击或哈希退化，应改用带随机种子的SipHash等算法。无论使用哪种哈希，槽位命中后都必须调用`flow_key_equal`确认。

参考：[RFC 9923：The FNV Non-Cryptographic Hash Algorithm](https://datatracker.ietf.org/doc/html/rfc9923)。

### TD-011：按最后活动时间清理过期流

状态：已采用。

决定：

使用`last_seen`和截止时间判断空闲流是否过期。哈希流表把过期槽位标记为`DELETED`，后续插入可以复用，但查找仍会越过该槽位继续探测；当流表完全为空时，再统一恢复为`EMPTY`。

主要理由：

- 长时间运行时，已结束连接不能永久占用流表；
- `last_seen`同时适用于离线PCAP时间和实时捕获时间；
- 截止时间由上层策略计算，流表只负责判断和移除；
- 删除标记既能释放业务容量，又不会破坏哈希冲突形成的探测链。

当前实现：

实时主循环使用30秒空闲超时和5秒扫描周期，在处理当前数据包前清理旧流。过期结果先复制给应用层再删除槽位，运行期间逐条输出，并与退出时仍留在流表中的记录分别计数。时间和所有权的详细选择见TD-023。

### TD-023：使用事件时间调度并在过期删除前返回流记录值副本

状态：已采用。

决定：

- 使用已观察数据包捕获时间戳的最大值作为事件时间高水位，乱序包不能让时间倒退；
- 第一版空闲超时固定为30秒，事件时间每推进5秒最多扫描一次；
- 扫描截止时间为`latest_timestamp - idle_timeout`，流表继续使用`last_seen <= cutoff`的包含边界；
- 当前包加入流表之前先执行到期扫描，避免沉默超过超时的同五元组会话被当前包刷新并错误合并；
- `flow_table_expire_before()`通过调用者提供的固定容量数组返回过期记录值副本，再清空原槽位；
- 应用层负责终端、CSV、Qt或队列等结果去向，流表和调度器都不直接依赖I/O。

为什么使用事件时间而不是直接读取系统时钟：

- 流记录的`last_seen`本来就来自libpcap数据包时间戳，使用同一时间域可以直接比较；
- 测试可以输入确定时间戳，不需要真实等待或模拟系统时钟；
- 最大值高水位能处理合并PCAP、多接口或时间校正导致的乱序；
- 直接使用`CLOCK_MONOTONIC`无法与捕获时间戳比较，除非每条流额外保存单调时钟活动时间；
- `CLOCK_REALTIME`虽然与常见PCAP时间接近，但系统校时可能发生跳变。

代价是完全没有数据包时事件时间不会推进，过期流要等下一包到来才输出。静默期间不会产生新流或继续增加流表压力；如果未来产品要求无流量时也准点上报，应为流活动增加单调时钟语义并接入定时事件，而不是混用两个时间域。

为什么返回值副本而不是槽位指针：

`flow_record_t`只包含流键、整数统计、时间戳和标志，不拥有动态内存，因此结构体赋值可以生成独立完整快照。删除时原槽位会被清零，返回指针会立即失去业务内容；值副本则可在槽位删除和复用后继续交给输出层。

为什么使用两遍扫描：

第一遍验证全部槽位、核对`count`并统计过期数量；只有输出容量足够时，第二遍才复制和删除。如果边扫描边删除，到中途发现缓冲区不足会留下部分修改状态。当前流表和快照数组都固定为256条，两遍线性扫描和额外有界栈空间换取清晰所有权及失败不修改语义。

验证：

- 单元测试覆盖5秒精确边界、差1微秒不提前扫描、乱序时间高水位和截止时间下溢；
- 流表测试确认过期值副本在槽位删除后仍完整，并验证输出容量不足不修改状态；
- 离线端到端验收确认实时策略没有改变完整PCAP聚合语义；
- `lo`接口使用两次间隔31秒的`ping -c 1 127.0.0.1`，观察到一条过期ICMP流和一条最终活动ICMP流；
- 该阶段完成时16项CTest通过；接入周期指标和非阻塞等待后，当前17项CTest通过。

复审条件：

- 需要在完全静默期间准点输出时，增加单调时钟活动状态和定时唤醒；
- 需要协议级生命周期时，为TCP、UDP和ICMP配置不同空闲超时；
- 流表容量扩大或接入线程后，评估分批快照、有界事件队列和背压，不允许重新出现“删除后没有结果所有者”的路径。

### TD-026：流表满载时拒绝新流数据包并继续分析

状态：已采用。

背景：

当前流表使用调用者提供的256个固定槽位。此前，当一条已完整解析的新流无法取得槽位时，`flow_table_process_packet()`返回`ENOSPC`，应用把它作为致命错误并结束整个分析。这能避免静默丢弃，却会让高基数流量直接终止长期运行的监控程序。

决定：

- 流表自身继续返回`ENOSPC`并保持失败不修改语义，不在底层隐藏容量问题；
- 应用层把新流插入的`ENOSPC`转换成`FLOW_REJECTED`处理结果，并继续读取后续数据包；
- 流表满载时，已经存在的流仍能被查找和更新，不计入拒绝；
- 周期报告和退出汇总都输出`flow_rejected`，使容量损失可观察；
- 默认策略不自动驱逐任意活动流，也不在本阶段引入动态内存扩容；后续增加的显式`evict-oldest`实时策略见TD-031。

计数语义：

`flow_rejected`统计的是“已经解析、但没有进入流表的数据包数量”，不是不同被拒绝流的数量。同一条未被记录的新流如果持续发送多个包，每个无法聚合的包都会增加该计数。若未来需要估算被拒绝的唯一流数量，应增加单独的数据结构或近似基数算法，不能把当前包计数改名解释。

为什么暂不自动驱逐：

- 固定容量使ARM目标上的内存上界明确；
- 在没有业务优先级时，随机驱逐、最旧驱逐和最低流量驱逐会产生不同的数据偏差；
- 现有事件时间过期已经能够回收真正空闲的槽位；
- 先报告占用率和拒绝数量，可以用真实压力数据决定扩容或驱逐策略。

验证：

- 确定性压力PCAP包含1个截断帧、1个畸形IPv4帧、1个不支持的ARP帧和257条不同ICMP流；
- 应用处理完全部260包并以成功状态退出；
- 最终分类为`complete=256`、`truncated=1`、`malformed=1`、`unsupported=1`和`flow_rejected=1`；
- 最终流表保留256条记录，证明第257条新流没有部分插入；
- Linux `lo`人工验收的60个ICMP包分别落入40包和20包两个周期，周期分类求和与最终`complete=60`一致；
- 全部17项CTest通过。

代价与复审条件：

- 满载期间的新流信息会丢失，当前只能知道被拒绝包数；
- 如果`flow_rejected`持续增加，应结合流表占用率、过期速率、CPU和内存数据评估容量；
- 需要优先保留特定协议或异常流时，应设计明确的准入与驱逐策略；
- 容量扩大、动态扩容或近似流统计都必须重新验证嵌入式内存上界和最坏情况延迟。

### TD-030：统计数据包路径的线性探测成本，再决定流表容量策略

状态：已采用。

背景：

流表占用率只能表示使用了多少槽，不能说明哈希冲突使一次查找实际检查了多少槽。直接根据“50%占用”或“满载拒绝”选择动态扩容、重建或驱逐，会把业务容量问题和哈希查找问题混在一起。

决定：

- 在`flow_table_process_packet()`的数据包路径累计操作次数、实际检查槽位总数和单次最大探测长度；
- 起始槽位计为1次检查，因此无冲突操作的探测长度为1；
- 已有流命中、新流插入和最终返回`ENOSPC`的完整扫描都计入；
- `flow_table_find()`和`flow_table_get()`等管理查询不计入，避免终端输出、测试或诊断改变被观测对象；
- 两个`uint64_t`累计值达到上限后保持饱和而不回绕，并显式输出`saturated=true`；饱和后平均值显示为不可用；
- 应用退出时输出累计快照，暂不把累计最大值混入按区间差分的周期指标。

验证与结果：

- 单元测试使用确定性冲突和回绕，验证探测长度1、2、3以及查询不污染统计；
- 满表`ENOSPC`计入完整容量，饱和计数不会回绕，失败查询保持调用者输出不变；
- 6包单流离线验收得到6次操作、6次槽位检查、平均和最大均为1；
- 128流、20万包、50%占用率的LubanCat复测得到`operations=200000`、`inspected_slots=200000`、`average=1.00`和`maximum=1`；
- 300流满载复测得到300次操作、11928次槽位检查、平均39.76和最大256；其中44次拒绝贡献11264次完整扫描，前256次成功建流共检查664个槽，平均约2.59；
- 两组板端测试均无应用分类缺口、捕获drop或接口drop，全部17项本地CTest通过。

结论：

当前受控128流工作负载没有哈希查找退化，不需要为了降低正常探测成本立即更换FNV-1a、重建流表或接入动态扩容。300流测试暴露的是固定256条同时活跃流的容量边界；下一步若要消除拒绝，应先定义业务上允许的内存上限和驱逐偏差，而不是把总体平均39.76误判为普通查找成本。

边界与复审条件：

- 128个临时源端口的受控流量不能代表任意五元组分布或恶意碰撞输入；
- 当前只输出运行期累计值，尚不能直接观察某一个5秒区间的最大探测长度；
- 如果正常负载的平均探测长度持续升高、最大值形成长尾、`flow_rejected`增加，或容量需要超过256，再评估可配置容量、重建、动态扩容或带明确偏差的驱逐策略；
- FNV-1a不是抗攻击哈希，如果真实威胁模型包含定向构造碰撞，应单独评估带随机种子的哈希算法。

### TD-031：实时满表使用单次探测选择并原位替换最旧流

状态：已采用。

背景：

固定256槽流表在300个不同UDP五元组测试中会拒绝后44个新流。默认拒绝能够保持内存上界并暴露容量损失，但长期实时监控还需要一种不中断新流观察的可选策略。策略必须同时说明淘汰偏差、被淘汰记录的所有权，以及当前包最终属于成功还是拒绝。

决定：

- 实时CLI增加`--flow-full-policy reject|evict-oldest`，默认继续使用`reject`，离线完整文件聚合不允许显式改变该策略；
- `evict-oldest`按`last_seen`选择最久没有活动的记录，而不是按`first_seen`选择最早创建的记录；
- 替换或删除前按值复制完整`flow_record_t`，因此输出不依赖之后被复用的流表槽位；
- 触发淘汰后成功插入的新流包仍计入`complete`，淘汰次数使用独立的`evicted_flows`事件计数，不能误记为`flow_rejected`；
- 应用层只选择`reject`或`evict-oldest`策略，不取得或修改物理槽位；
- `flow_table_process_packet_with_oldest_eviction()`与默认拒绝路径复用同一个内部处理函数。在正常线性探测中同时记录`last_seen`最小的已占用槽位，但只有探测完全部容量、确认新键不存在且没有`EMPTY`或`DELETED`槽位时，才把该候选用于淘汰；
- 替换前先在局部变量中完整初始化新`flow_record_t`，再按值复制被淘汰记录，最后用新记录覆盖最旧的`OCCUPIED`槽位。槽位状态保持`OCCUPIED`，`count`保持不变，调用者只得到记录值副本和`evicted`布尔值；
- 无效参数、无效数据包或流表内部计数与物理槽位不一致时返回错误，并保持记录、输出参数和探测统计不变。

为什么原位替换必须封装在流表内部：

- 开放寻址通常要求记录位于自身哈希起点能够到达的探测链上；任意把新记录放到链外槽位时，后续查找可能先遇到`EMPTY`并错误地报告不存在；
- 这次原位替换只发生在已经扫描完整个表并验证每个槽位均为`OCCUPIED`的场景。表中没有会提前终止查找的`EMPTY`，因此从任意哈希起点线性探测都能到达替换槽位；`OCCUPIED`到`OCCUPIED`的替换也不会破坏探测链；
- 候选下标和槽位生命周期继续封装在流表模块内部；应用层只取得值副本，不能绕过`state`、`count`和失败不修改约束；
- 独立的`flow_table_evict_oldest()`仍可作为管理接口使用，但实时数据包路径不再通过“删除后重试”组合它。

验证：

- Ubuntu `lo`使用BPF `udp and dst portrange 30000-30299`产生300个不同UDP五元组；
- `evict-oldest`得到`complete=300`、`flow_rejected=0`、`Evicted flows: 44`和最终`Flow summary: 256 flow(s)`；
- 捕获drop和接口drop均为0；
- 探测统计为`operations=344`、`inspected_slots=25055`、`average=72.83`和`maximum=256`，其中344次操作等于300次首次处理加44次淘汰后重试；
- 官方SDK ARM64 Release产物在LubanCat-2N物理网卡使用300个不同UDP五元组复测，得到`complete=300`、`flow_rejected=0`、`Evicted flows: 44`、最终256条流、后端接收300包和两个drop字段为0；
- 板端探测统计为`operations=344`、`inspected_slots=25505`、`average=74.14`和`maximum=256`。检查槽位数与虚拟机不同，来自源地址、端口和哈希分布差异；操作数、淘汰数和容量结果保持一致；
- 上述Ubuntu和板端结果是优化前基线；优化后的Ubuntu `lo`复测得到`operations=300`、`inspected_slots=12416`、`average=41.39`、`maximum=256`、`complete=300`、`flow_rejected=0`、44次淘汰和最终256条流，两个drop字段仍为0；
- 优化后的官方SDK ARM64产物在LubanCat-2N复测得到`operations=300`、`inspected_slots=15364`、`average=51.21`、`maximum=256`、`complete=300`、`flow_rejected=0`、44次淘汰、最终256条流和两个drop字段为0；后端累计接收303包不等于应用处理计数，也不改变专用drop字段的结论；
- 44条按时间依次产生的最旧流被逐条输出，端口范围从30000到30043，与预期淘汰顺序一致；
- 单元测试覆盖普通插入、已有流更新、满表原位替换、容量与查找结果、每包一次探测操作，以及无效参数、无效包、内部计数损坏和失败输出不变；本地17项CTest全部通过，`git diff --check`通过。

优化效果与边界：

- 旧实现中，每个满表新流执行一次256槽满表探测、一次未进入探测统计的256槽最旧记录扫描，再执行一次256槽插入重试。44次淘汰对应11264次已报告的重试槽位检查，以及11264次未报告的独立淘汰扫描；
- 新实现把三次整表扫描收敛为一次。`operations`从344降到300，直接证明44次重试探测已经消除；按固定容量计算，满载路径同时省去的两轮额外扫描最多为22528次槽位访问；
- Ubuntu的`inspected_slots=25055`与`12416`以及板端优化后的15364都不能直接计算严格的跨轮次或跨平台性能提升百分比，因为实时流量使用的源端口、NAT结果和哈希分布不同。要量化CPU收益，仍需使用完全相同的五元组序列、发生速率和构建产物进行成对测试；
- 每次正常探测现在会顺带比较已占用槽位的`last_seen`，即使流表没有满也有少量固定工作。当前容量仅256，正确性和边界测试均通过；若未来扩大容量或高换入率成为主要负载，再用受控基准复核CPU和drop。

## 8. 并发、输出与异常检测

### TD-013：单线程正确后再接pthread流水线

状态：实验完成，正式接入暂缓。

决定：

正式链路先保持单线程；性能和接口稳定后，采用固定角色线程与有界阻塞队列连接采集、解析、流聚合和输出。

主要理由：

- 单线程更容易验证协议字段和所有权；
- 线程不能修复算法问题，过早并发会增加竞态、关闭顺序和调试成本；
- 项目已经通过`labs/thread_pipeline`验证生产者、处理者、输出者、条件变量和优雅退出；
- 固定流水线角色比通用线程池更符合当前数据处理顺序。

复审条件：

接入前先用性能数据确认瓶颈。如果抓包速度、解析速度和输出速度差异明显，再确定线程数量、队列容量和背压策略。

当前实测结论：

- LubanCat ARM64原生Release在约8.8～9.1 Kpps时处理20万包，进程平均CPU约4.25%；
- 每包整体CPU成本约6.95微秒，最大RSS约1.64 MiB，应用拒绝与两个drop字段均为0；
- 当前范围没有显示单线程瓶颈，也没有出现需要用队列隔离的持续背压。

因此正式程序暂不接入线程流水线；后续只有在更高PPS、多流、应用层解析或输出阻塞数据证明瓶颈后再复审。

### TD-014：先结构化输出，再做Qt和云端

状态：基础完成。

决定：

核心程序先提供CSV流记录格式化接口，Qt上位机和可选云端再消费稳定的数据接口。CSV第一版使用独立的协议号、IP地址、端口、双向统计和时间戳字段；输出模块只借用调用者提供的`FILE *`，文件路径和生命周期由应用层负责。Qt优先用于求职展示和本地调试，云端只在需要远程监控时增加。

主要理由：

- GUI不应该直接读取核心内部结构；
- 稳定的结构化输出可以同时服务测试、Python、Qt和远端上传；
- Qt适合展示实时流列表、协议分布和告警；

为什么第一版选择CSV：

- 当前流记录是固定列的扁平数据，适合表格格式；
- C标准库即可生成，不需要额外JSON依赖；
- Python、Qt、电子表格和常见数据分析工具都能直接读取；
- 当前字段只有整数和IPv4文本，不包含逗号、引号和换行，暂时不需要复杂转义。

边界与后续：

普通流记录CSV格式化模块、`--csv FILE`命令行参数和端到端文件验收已经完成。应用层在流聚合成功后打开文件，导出器只借用`FILE *`，应用层最终检查`fclose`结果。文件使用C11的`wx`模式独占创建，避免误覆盖已有CSV或输入PCAP。模型特征使用独立的版本化CSV契约，见TD-036；两种格式不共用路径或混写列。以后出现嵌套应用层数据、告警详情或远端API时，再增加JSON，而不是用CSV勉强表达层级结构。

### TD-036：使用版本化流特征契约，并在流生命周期结束时导出

状态：已采用第一版。

背景：

普通流记录CSV面向调试和完整业务记录，包含端点身份、双向原始统计和时间戳。训练与在线推理则需要稳定、含义明确且能够跨环境复用的模型输入列。如果直接让Python脚本临时解释普通CSV，训练端和部署端容易在字段顺序、单位、类别编码或计算公式上逐渐分叉。

决定：

- 在C核心中使用`flow_features_from_record()`把已初始化的`flow_record_t`转换为不拥有动态内存的`flow_features_t`；训练数据生成与未来在线推理必须复用同一套持续时间、总量、均值、方向不平衡度和TCP状态语义；
- 使用`flow_features_v1`作为第一版CSV模式标识，字段名称、顺序、单位和非TCP表示都属于版本化契约；`schema_version`是解析元数据，不作为模型输入；
- `protocol`和`tcp_phase`是类别特征，数值或枚举顺序不代表距离；均值和方向比率使用`double`，不平衡度固定在0至1；
- 第一版不输出IP地址和端口，降低模型记忆特定设备、网段和服务标识的风险；也不输出异常标签，标签必须由后续公开数据集映射或受控采集流程提供；
- 每条流在本次生命周期结束时输出一次：实时过期记录在删除时输出，容量淘汰记录在槽位覆盖前输出，采集停止后输出最终剩余记录；三组值副本互不重叠，合起来覆盖有限采集中的完整流集合；
- 离线模式允许同时生成普通流CSV与特征CSV，但要求不同路径。实时特征导出必须提供大于0的`--count`，不允许无上限systemd服务持续增长单一文件；
- 特征文件由应用层包装函数以`"wx"`独占创建、写一次表头并在所有路径调用`fclose()`。分析函数和导出器只借用`FILE *`，不能关闭或保存该指针；业务错误与关闭错误同时出现时保留更早的业务错误。

主要理由：

- 把特征公式放在C核心，能够避免“公开数据集训练脚本一套公式、开发板实时推理另一套公式”的训练—服务偏差；
- 在流生命周期结束时导出，才能得到稳定的持续时间、总量和TCP阶段，同时避免逐包重复输出同一条不断变化的流；
- 过期和淘汰会让记录在最终遍历前离开流表，必须在离开点使用值副本立即输出，否则训练数据会系统性遗漏短流或容量压力下的流；
- 固定模式版本使后续字段变更能够显式升级，而不是静默改变旧模型输入含义；
- `wx`和有限实时任务把错误覆盖、无限写盘和8GB目标板容量风险变成启动前可验证的约束。

没有选择：

- 没有把普通流记录CSV直接称为模型数据集，因为它同时承担调试语义、端点身份和原始统计，不是稳定的模型输入契约；
- 没有每收到一个包就输出特征快照，因为这会对长流产生大量相关重复样本，并让“流结束状态”失去统一含义；
- 没有在第一版加入IP、端口或标签，因为身份字段可能造成数据泄漏，标签也不能由流量分析器自行猜测；
- 没有为无上限实时服务加入自动轮转，因为文件轮转、恢复、配额和下游消费需要独立的持久化设计，不能用一个CLI开关隐式完成。

验证：

- `flow_features_tests`覆盖TCP/UDP特征、持续时间借位、总量与均值、方向不平衡度、协议状态不变量、无效时间和整数溢出，并检查失败不修改调用者输出；
- `flow_feature_export_tests`覆盖固定表头、TCP与非TCP记录、布尔编码、浮点精度、协议状态和非法数值；
- Python离线验收使用确定性6包ICMP PCAP核对完整的`flow_features_v1`数据行，并确认已有目标文件不会被覆盖；
- x86_64 Debug构建的20项CTest全部通过；
- Ubuntu实时过期验收得到一条2包过期流和一条4包最终剩余流；300个单包UDP流的最旧流淘汰验收得到44条淘汰记录和256条最终记录，特征文件共300条数据行。

边界与复审条件：

- 特征文件自身仍不包含样本ID、IP、端口或标签；第一版已经通过独立`flow_sample_metadata_v1` sidecar保存这些连接信息。使用方必须验证模式版本、行数和同一次分析的输出顺序，不能把任意特征文件与任意元数据文件按行拼接；
- 公开数据集若不能提供原始PCAP或等价字段，必须记录缺失字段、单位换算和不可复现特征，不能伪造完全一致；
- 当前只完成特征生成，没有规则异常判定、Python模型训练、模型格式、阈值选择或ARM64在线推理；
- 特征列、单位、类别编码或归一化方式发生变化时，应升级模式版本并保持旧解析逻辑可识别，而不是继续沿用`flow_features_v1`。

### TD-038：离线流分段使用可选事件时间空闲阈值

状态：已采用第一版。

决定：

- 新增`--flow-idle-timeout SECONDS`，只允许与离线`--read`组合，并要求能表示为正的`int64_t`秒数；
- 未指定选项时保留原有“同一流键跨整份PCAP聚合”语义，不为旧用户和已有测试静默改变流边界；
- 启用后复用已有事件时间高水位与5秒扫描调度，扫描仍发生在当前包进入流表之前；
- 过期记录按值复制后同时进入终端、普通流CSV和特征CSV的既有生命周期输出路径，随后同键新包创建新流；
- 阈值是明确、可重现、可审计的项目配置，不声称复制Argus的私有超时、状态或轮转规则。

主要理由：

- 离线数据应由PCAP时间戳驱动，使处理结果不依赖分析机速度、真实时钟或`sleep`；
- 对同一五元组进行空闲分段，可以避免数分钟后的新会话继续累加到旧特征中，也为公开标签匹配实验提供可控流边界；
- 保持默认关闭可以把“功能能力”与“为某数据集选择阈值”分开，避免在没有证据时把30秒当成通用正确值。

验证：

- CLI测试覆盖有效值、0、负数、溢出、重复选项和实时模式错误组合；
- 确定性离线PCAP使用同一双向ICMP流键，第一个生命周期为2包，空闲约39秒后的第二个生命周期为4包；
- `offline_flow_acceptance`精确验证`Expired flows: 1`、两条普通流CSV和两条`flow_features_v1`记录，并恢复了已定义但之前未被调用的TCP三次握手验收子用例；
- x86_64 Debug构建当前共24项CTest且全部通过；Release、Sanitizer和ARM64基线尚未因本功能重新配置验证。

边界与下一步：

- 空闲阈值只解决“何时结束当前聚合流”，不解决重叠候选如何变为唯一匹配、截断TCP如何恢复或模型该使用哪些特征；特征行与身份/标签的稳定连接已由第一版sidecar完成；
- Scenario 7恶意DNS子集已经完成候选空闲阈值扫描；5秒只是在当前五元组模型下兼顾唯一匹配数与碎片数量的实验候选，不是Argus真值。公开42字节UDP捕获缺少DNS事务ID，不能通过继续调参完整重建官方事务边界；下一步转为评估可可靠生成监督样本的数据方案，不将歧义样本静默加入训练集。

### TD-039：使用稳定样本ID和sidecar元数据连接特征与监督标签

状态：已采用第一版。

背景：

`flow_features_v1`有意不包含IP、端口和标签，避免模型直接记忆设备、网段或服务；但监督训练仍必须知道“某一特征行来自哪次抓包、哪条规范化流生命周期、匹配到了什么标签以及匹配是否可靠”。把身份列重新塞入特征CSV会混淆模型输入与数据治理元数据，仅依赖文件行号又无法跨文件验证样本身份。

决定：

- 模型特征继续保留在`flow_features_v1`，身份和监督连接另存为`flow_sample_metadata_v1` sidecar；端点、时间和标签不会自动成为模型输入；
- `FlowSampleIdentity`由`capture_id`、协议、规范化双向端点、`first_seen`和`last_seen`的Unix微秒组成。对象不可变，端点顺序、ICMP零端口、字段类型和整数范围都必须先通过验证；
- `sample_id`使用`flow_sample_id_v1:`前缀。实现把模式版本和全部身份字段按固定顺序序列化为紧凑ASCII JSON，再计算SHA-256十六进制摘要；SHA-256用于提供低碰撞、确定性的内容标识，不把该ID当作签名、密钥或标签；
- sidecar以从1开始的`feature_row_number`连接同一次分析产生的特征数据行，并同时保存元数据/特征模式版本、`sample_id`、完整身份、匹配状态、候选数、标签组和`is_trainable`；
- 匹配状态固定为`unique`、`unmatched`、`ambiguous_same_label`和`ambiguous_conflicting_labels`。只有`unique`且标签为`benign`或`malicious`时`is_trainable=1`；其余记录保留审计证据但不能静默进入监督训练；
- 审计CLI要求`--capture-id`与`--metadata-output`成对出现。目标文件以独占模式创建，不覆盖旧证据；处理失败时尝试删除本次产生的不完整文件；库函数只借用调用者提供的文本流，不关闭或保存它。

主要理由：

- 特征、身份和标签职责分离后，可以在不改变模型输入模式的情况下重新审计标签规则和匹配阈值；
- 稳定ID比裸行号更适合发现抓包来源、端点或生命周期发生变化，模式前缀允许未来升级规范化规则；
- 显式保存匹配状态和候选数量，能防止“有候选”被误写成“有可靠标签”，也为后续比较不同空闲阈值保留质量证据；
- 独占创建和失败清理延续C端CSV输出的文件生命周期约束，避免旧结果被覆盖或半成品被误当作完整数据集。

验证：

- 固定向量测试验证相同身份得到相同ID，修改抓包ID或任一身份字段会改变ID，非规范端点、错误类型、非法范围和不支持协议会被拒绝；
- 元数据测试验证不可变对象、四种匹配状态不变量、`is_trainable`、固定CSV表头与内容、写入前重新验证、失败不写半行以及输出流仍由调用者拥有；
- 合成匹配审计为5条C流生成连续的特征行号、四种匹配状态和唯一的样本ID，并验证内存输出与CLI文件完全一致；
- CLI测试验证参数必须成对、已有文件不覆盖、失败后不保留不完整输出；x86_64 Debug构建24项CTest全部通过。

边界与复审条件：

- `feature_row_number`只在普通流CSV与特征CSV来自同一次分析、相同生命周期参数且保持相同输出顺序时有效；后续训练集构建器必须先检查模式版本、数据行数和对应关系；
- 稳定ID只描述当前规范下的样本身份，不证明标签正确，也不能解决Argus与本项目流边界不同、公开TCP截断或候选重叠问题；
- 当前真实Scenario 7审计仍只有47条未匹配背景流和2条同标签歧义恶意DNS流，没有可靠的一对一训练样本；下一步先用候选空闲阈值重跑审计，再决定是否扩展更多场景或数据集。

### TD-024：按文件系统语义和容量分配eMMC与SD卡职责

状态：已采用。早期“VFAT源码、eMMC构建”的过渡布局已经因目标镜像的自动挂载与自动扩容冲突而停止使用；新的eMMC布局已完成工作树恢复和板端回归，SD数据盘也已完成唯一自动挂载和普通用户读写验收。

决定：

- Git源码恢复到eMMC的ext4目录`/home/cat/workspace/netflow-analyzer`，活动Debug和Release构建树继续放在`/home/cat/build`；
- 板端只保留当前验证所需的源码和少量活动构建树，不在eMMC长期积累大型PCAP、历史日志、软件包缓存或大量旧构建；
- 原生兼容性验证完成后，优先评估在开发电脑交叉编译，板端只保留Release程序和运行依赖；
- SD卡由`usbmount`以`uid=1000,gid=1000,dmask=0022,fmask=0133,noexec,nodev`自动挂载，只用于PCAP、CSV、数据集和日志等大容量数据；如果未来确实要在SD卡长期板端编译，再评估独立ext4分区；
- 不让`usbmount`、`/etc/fstab`和手工挂载同时管理同一分区；挂载策略必须有唯一所有者；
- 当前eMMC根文件系统已经完成扩容，屏蔽会遍历`/proc/mounts`的厂商`resize-all.service`，避免它再次处理可移动数据卡；
- 不为了从VFAT直接运行ELF而把整个分区上的普通文件统一设为可执行。

主要理由：

- eMMC上的ext4支持完整Linux语义，但8GB容量在安装系统后余量有限；
- CMake和编译器会产生大量临时文件、静态库与可执行程序，构建树需要可靠的Unix权限；
- Git会跟踪文件名和可执行位，长期把工作树放在VFAT上可能出现权限噪声、大小写冲突或符号链接限制；
- PCAP和CSV是普通数据文件，不依赖Unix执行权限，适合放在容量可扩展且便于移动的SD卡；
- 实机事故证明，厂商`resize-all.service`并没有把处理范围严格限制为板载系统盘：脚本枚举`/proc/mounts`，对VFAT进入重新创建文件系统的回退路径，而失败的恢复又因`set +e`被最终成功退出码掩盖；
- 项目源码和两个构建树此前合计只有约10MB量级，相对于当前eMMC剩余空间仍很小；把它们放在ext4所获得的正确性和可维护性高于这部分容量成本。

实测空间：

```text
eMMC根分区：7.0GB，总占用5.4GB，可用1.4GB，使用率81%
当前源码树：2.4MB
当前Debug构建树：3.2MB
事故前SD卡项目目录：7.2MB
```

源码与当前Debug构建树合计约5.6MB，远小于1.4GB可用空间，不构成立即容量压力。新构建树在eMMC绝对路径下完成当前18项板端CTest，证明新布局同时满足Git和构建执行语义。真正需要控制的是未来PCAP、机器学习数据集、长期日志、软件包缓存和多个大型构建树，而不是当前项目工作树本身。

SD卡恢复时先以`fsck.vfat -n`完成只读检查并得到退出状态0；随后跨重启确认`resize-all.service`保持`masked`，`/dev/mmcblk1p1`只有一个`/media/usb0`挂载记录。普通用户完成临时文件的创建、31字节写入、同步、读取和删除，文件与目录分别呈现`0644`和`0755`。这证明“eMMC运行、SD存数据”的分工已经从设计决定进入实机可用状态。

代价与复审条件：

- 当前可以在eMMC同时保留源码及Debug、Release活动构建树，不需要为了数MB空间提前删除可重建但仍有使用价值的目录；
- eMMC承载短期原生验证的写入量可接受，但不适合在空间紧张时长期积累多个构建目录；
- 如果PCAP写入速率、SD卡寿命或容量成为瓶颈，需要测试介质持续写入性能和掉电行为；
- SD卡格式化或重新分区会清除数据，必须先备份并确认精确目标，不能作为无风险操作；
- 如果未来系统镜像升级、重新烧录或确实需要再次扩容，应先移除数据卡并复审`resize-all.service`，不能直接取消屏蔽；
- 正式服务化部署时再确定程序、配置、运行数据和日志是否分别进入`/usr/local`、`/etc`、`/var/lib`和`/var/log`。

- 数据包列表类型使用`typing.List`和`typing.Tuple`，不使用Python 3.9才支持的`list[...]`和`tuple[...]`内置泛型注解；
- 不为了运行项目测试替换或升级板端系统Python；
- Python继续只作为`BUILD_TESTING=ON`时的验收依赖，不进入正式程序运行依赖。

主要理由：

- 测试工具本身必须能在目标系统运行，否则无法区分测试基础设施故障与C程序故障；
- 板端发行版提供的系统Python可能被系统工具和软件包依赖，单独升级会增加环境破坏和维护风险；
- 当前脚本只使用标准库，没有必须要求Python 3.9的新功能；
- `typing.List[typing.Tuple[...]]`保持相同类型信息，并兼容Python 3.8。

验证：

- 修改后LubanCat ARM64原生Debug构建的目标验收和全量17项CTest通过；
- 验收脚本能够实际启动分析器并完成确定性PCAP检查。

代价与复审条件：

### TD-029：用Release外部负载基线决定是否引入并发

状态：已采用。

决定：

- 性能结论使用目标板Release构建，不使用Debug数据代替；
- 流量由外部虚拟机产生，避免把发生器CPU混入目标进程；
- 同时记录应用分类、PPS/Mbps、libpcap drop、进程CPU时间和最大RSS；
- 当前基于实测继续保持单线程，不为展示技术栈而提前接入pthread流水线。

证据：

- 空闲22.04秒时进程CPU时间0.01秒，最大RSS 1764 KiB；
- 4万包、约1.8 Kpps时进程CPU时间0.29秒，整体成本约7.25微秒/包；
- 20万包、约8.8～9.1 Kpps时进程CPU时间1.39秒，整体成本约6.95微秒/包；
- 128流、20万包、50%流表占用率时整体成本约6.70微秒/包，零拒绝和零drop；
- 128流、540万包、约9 Kpps连续10分钟时整体成本约6.24微秒/包，`pidstat`首尾RSS均为564 KiB，最大RSS 1764 KiB；
- 300个不同UDP五元组精确得到256个`complete`和44个`flow_rejected`，证明满载后继续运行策略有效；
- 长稳窗口内整机平均空闲90.97%，CPU0软中断8.00%，没有应用单核或软中断饱和证据。

边界：

- GNU `time`记录目标进程及子进程资源，不完整覆盖网卡软中断等整机开销；整机补测使用`mpstat`单独观察，不能把两类百分比直接相加；
- 本轮是单条ICMP双向流，不代表多流哈希、TCP/UDP或应用层解析成本；
- 短时测量不能替代长时间内存稳定性测试；
- 达到更高负载、出现drop、输出阻塞或单核接近饱和时重新评估线程数量、队列容量和包数据所有权。
- 如果更高PPS首先使CPU0软中断饱和，应先评估网卡队列、IRQ亲和性和RPS，避免把内核收包瓶颈误判为应用解析线程不足。

详细方法和原始结果摘要见[`docs/performance_baseline.md`](performance_baseline.md)与[`docs/multiflow_longrun_baseline.md`](multiflow_longrun_baseline.md)。

### TD-032：用每流旁路状态机建立TCP生命周期语义

状态：已采用第一版。

决定：

- 每条TCP `flow_record_t`按值保存独立的`tcp_flow_state_t`，UDP和ICMP保持该对象未初始化；
- 状态机消费规范化流方向和TCP标志，识别`unobserved`、`syn-seen`、`syn-ack-seen`、`established`、`midstream`、`fin-seen`、`fin-bidirectional`、`closed`和`reset`；
- `endpoint_a`和`endpoint_b`只来自五元组排序，不能当作客户端和服务器；发起方向只有观察到不带ACK的初始SYN后才建立；
- 抓包从连接中途开始时进入`midstream`，不根据后来偶然出现的标志倒推出一次完整握手；
- RST优先于其他标志并立即进入`reset`；相同方向FIN视为重传，两个方向均出现FIN后再由最先发送FIN的一方发出的ACK进入`closed`；
- `closed`和`reset`作为第一版终止状态，迟到包和重传不会重新打开旧记录；
- 状态名称由核心模块统一提供，终端和CSV不得各自维护不同映射；非TCP输出使用`not-applicable`，而不是伪造一个TCP阶段。

主要理由：

- 仅解析单包TCP头无法回答连接是否完成握手、是否从中途开始观察、是否正常关闭或被RST中止；
- 每流状态是后续SYN完成率、大量失败连接、连接持续时间、规则检测和机器学习特征的基础；
- 状态对象只含枚举、方向和布尔值，不拥有动态内存，适合当前固定容量流表的复制、过期与淘汰语义；
- 把名称转换放在状态模块可保证CLI、CSV、Qt和未来事件模型共享同一含义。

没有选择：

- 没有复制Linux内核完整TCP状态机。旁路分析器看不到socket调用和全部内核事件，也可能从连接中途开始抓包；
- 没有仅以`SYN`包数减`SYN+ACK`包数代替状态机，因为那无法表达方向、重传、正常关闭和每流历史；
- 没有在当前步骤直接实现字节流重组。状态跟踪只消费标志，重组还需要序列号窗口、重复与重叠处理、乱序缓存、内存上限和超时策略。

验证与当前边界：

- 单元测试覆盖双向发起、SYN和SYN+ACK重传、完整握手、中途捕获、无效方向、FIN关闭、RST和终止状态；
- 流记录测试验证首包和后续包共同推进状态，并验证非TCP流不拥有TCP状态；
- 确定性3包PCAP端到端验证终端与CSV均输出`established`，ICMP CSV输出`not-applicable`；
- x86_64与LubanCat-2N ARM64原生Debug构建的18项CTest全部通过；
- LubanCat-2N的`lo`上使用HTTP/1.0真实连接完成运行验收：应用处理12个TCP包，全部为`complete`，双向各6包并聚合为1条流，最终状态为`closed`，两个drop字段均为0；
- 捕获后端报告`received=24`而应用处理12包，属于Linux回环捕获后端与应用交付层的统计口径差异，不解释为应用重复处理或丢包；
- 当前不核对ACK号是否精确确认SYN/FIN，不处理乱序字节、TCP选项、重组或同一五元组在终止状态后的重新建连；


### TD-033：把可选包数上限与服务生命周期分离

状态：已采用，作为systemd服务化前置。

决定：

- 实时模式只提供`--interface NAME`时持续运行，直到收到`SIGINT`、`SIGTERM`或致命错误；
- `--count PACKETS`保留为可选的有限测试与人工验收上限，显式参数仍必须为正整数；
- `app_context_t.packet_limit == 0`只是内部的“无上限”哨兵值，启动输出显示`Packet limit: unlimited`而不是容易误解的0；
- 有限与无上限模式复用同一采集循环、信号处理和清理路径，只在包数终止条件上分支。

主要理由：

- systemd服务的自然生命周期是持续运行，由服务管理器发送`SIGTERM`停止；
- 使用特别大的`--count`伪装无限运行仍会耗尽，且把部署语义错误地绑定到`size_t`范围；
- 已有信号中断、非阻塞poll等待和正常清理路径，不需要为服务寿命新增定时线程、忙轮询或另一套退出逻辑。

验证：

- 参数测试同时覆盖省略`--count`的无上限模式、合法正整数上限，以及显式0、非数字和缺少参数值；
- 本机18项CTest全部通过；
- `lo`上省略`--count`并使用`icmp` BPF，静默期先输出0包周期报告，随后处理4个`complete`包，`SIGTERM`后正常输出汇总；后端`received=8`，两个drop字段均为0。


### TD-034：由程序显式保证服务日志按行刷新

状态：已采用，已完成systemd板端复验。

决定：

- 在`main()`开始、stdout发生任何I/O之前调用`setvbuf(stdout, NULL, _IOLBF, 0)`；
- stderr保持C运行库的既有错误输出语义，不为周期日志增加额外线程；
- systemd继续使用`StandardOutput=journal`和`StandardError=journal`，不在服务单元中依赖`stdbuf`包装程序；
- 如果stdout缓冲模式无法建立，启动立即失败并向stderr输出固定错误，而不是进入日志不可预测的长期运行状态。

主要理由：

- stdout连接交互式终端时通常按行缓冲，连接普通文件、管道或systemd journal时可能变成全缓冲；
- 周期指标是长期服务的健康信号，如果要等缓冲区填满或进程退出才出现，`journalctl -f`就不能反映当前运行状态；
- `stdbuf`适合临时Shell测量，但会增加外部命令和运行环境依赖，不能作为服务自身的日志契约；
- 显式行缓冲只影响输出刷新时机，不改变抓包、解析、流表所有权或单线程数据路径。

为什么“以前用了管道也能看到”不能否定该选择：

- `sudo`可能为被执行程序分配伪终端，程序看到的stdout仍然是终端；
- 全缓冲在缓冲区填满时仍会成批输出，`tee`会保持行的排版，但不能证明每行实时到达；
- 正常退出会刷新C标准I/O缓冲，事后查看完整日志不能证明运行中已经写入。

验证：

- 本机构建和18项CTest继续通过；
- 人工测试让重定向发生在`sudo sh -c`内部，使分析器stdout直接连接普通文件；
- 在12秒进程结束前，第7秒已经能够从文件读到第一条5秒周期报告，证明换行日志在真正的非终端输出环境中及时发布；
- LubanCat-2N服务仍在运行时，journal已经显示静默期5秒报告；真实ICMP流量和`SIGTERM`停止后的最终汇总也完整进入journal，证明程序级行缓冲在目标服务环境生效。


### TD-035：使用专用系统用户和systemd动态能力边界运行抓包服务

状态：已采用第一版，手工启停、开机自启、异常恢复和连续失败限速验收通过，服务长稳待验证。

决定：

- 程序、配置和服务单元由`root:root`拥有，运行进程使用无登录、无home目录的`netflow-analyzer`系统用户和同名组；
- 不让分析器长期以root运行，也不把文件capability永久写入ELF；
- systemd通过`AmbientCapabilities=CAP_NET_RAW`把原始网络访问能力交给服务进程，通过`CapabilityBoundingSet=CAP_NET_RAW`限制可获得能力的上限；
- 使用`NoNewPrivileges=yes`阻止进程及其子进程在后续`exec`中扩大权限；
- 第一版不授予`CAP_NET_ADMIN`，因为程序不配置接口、地址、路由或防火墙；
- 首次部署只执行手工`start`和`stop`，验证完成后再单独启用开机启动。

主要理由：

- libpcap实时打开Linux packet socket需要`CAP_NET_RAW`，但协议解析和流聚合不需要完整root权限；
- root拥有磁盘文件可以防止服务进程利用自身漏洞改写下一次启动的程序或配置；
- systemd动态能力属于进程生命周期，升级替换ELF时不会遗留难以发现的文件扩展属性；
- bounding set和no-new-privileges形成两道明确上限，便于通过`/proc/PID/status`审计；
- 把启动、停止、异常重启、日志和权限统一交给systemd，比在Shell后台运行或使用`sudo`包装长期进程更可观察。
- 显式使用`StartLimitIntervalSec=30s`和`StartLimitBurst=5`，让短暂接口繁忙获得多次恢复机会，同时让持续配置或硬件错误停止无限进程创建和日志刷写；达到上限后由管理员排除根因并显式恢复。

没有选择：

- 没有使用root服务，因为权限范围远超当前业务需要；
- 没有使用`sudo netflow-analyzer ... &`，因为它没有完整的服务依赖、重启、日志和开机生命周期模型；
- 没有使用`setcap`给二进制永久授予能力，因为文件替换、备份和权限审计更容易出现状态差异；
- 没有把服务用户设为程序文件所有者，避免运行进程能够修改自身可执行文件。

验证：

- 官方SDK为提交`740d5ab`生成的部署包SHA-256为`f916176829974d61ff853310638fd0b07c8570f715d97f67238aebfad259c55d`，两端传输摘要一致；
- ARM64 ELF在板端通过`file`、`ldd`和`--version`检查；
- systemd静态检查、单元加载、专用用户/组和手工启动通过；
- 进程实际UID/GID为`netflow-analyzer`，有效、边界和ambient capability只包含`0x2000`，即`CAP_NET_RAW`，`NoNewPrivs=1`；
- 虚拟机发送2次ping后，服务完整处理4个ICMP包并聚合为1条双向流；4次流表操作均只检查1槽，两个drop字段为0；
- `systemctl stop`触发SIGTERM正常收尾，最终活动流汇总进入journal，没有异常重启；
- 执行`enable`和受控重启后，boot ID发生变化；没有人工`start`时服务已为`enabled`和`active`，`Result=success`、`NRestarts=0`；
- 新boot中的新PID仍使用专用UID/GID和唯一`CAP_NET_RAW`能力，journal静默报告与再次发送的4个ICMP包均正确；
- `critical-chain`确认单元排在`network-online.target`之后；该顺序不被解释为互联网或所有接口必然可用，异常网络恢复仍保留单独复审；
- 后续一次真实重启中，第一次进程打开`eth0`时因`ETHTOOL_GET_TS_INFO`返回`EBUSY`而非零退出；`Restart=on-failure`等待2秒后创建第二个进程，后者成功打开接口并持续发布周期报告，`NRestarts=1`准确保留了恢复历史；
- 当前继续让接口打开失败结束进程并由systemd统一重启，不在C应用中叠加第二套重试状态；不存在接口的可重复实验以30秒窗口和5次上限连续创建5个失败进程，第6次被`Start request repeated too quickly`拒绝；

## 12. 面试表达原则

介绍技术选型时按照以下顺序说明：

```text
业务场景
  → 当前约束
  → 选择的方案
  → 没选其他方案的原因
  → 当前方案的代价
  → 测试或数据如何验证
```

例如FNV-1a的完整表达不是“因为它快”，而是：五元组只有13个业务字节，需要低开销、无动态内存、跨x86与ARM稳定的非加密哈希；FNV-1a实现短小且有固定参考流程，因此适合作为第一版。代价是不能防御恶意碰撞，所以哈希命中后仍比较完整流键，并保留未来改用带随机种子算法的条件。
