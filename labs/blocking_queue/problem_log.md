# 有界阻塞队列实验问题记录

## 1. 我的实验目标

我通过本实验学习和验证了以下 Linux 多线程知识：

- POSIX线程的创建与回收；
- 互斥锁对共享状态的保护；
- 条件变量的等待和唤醒；
- 有界环形队列的满、空和下标回绕；
- 生产者与消费者模型；
- 队列关闭和线程安全退出；
- 多线程测试与压力测试。

我把队列容量设置为4，以便频繁触发队列满、队列空和数组下标回绕。

## 2. 我最终实现的行为

我为队列实现了以下接口：

- `blocking_queue_init`：初始化队列、互斥锁和条件变量；
- `blocking_queue_push`：写入数据，队列满时等待`not_full`；
- `blocking_queue_pop`：取出数据，队列空时等待`not_empty`；
- `blocking_queue_close`：关闭队列并唤醒全部等待线程；
- `blocking_queue_destroy`：销毁条件变量和互斥锁。

我最终确定的关闭语义是：

- 关闭后禁止继续写入；
- 关闭前已经存在的数据仍然可以取出；
- 队列关闭且取空后，`pop`返回`ECANCELED`；
- 等待`not_empty`或`not_full`的线程会被`close`唤醒。

## 3. 我遇到的问题

### 3.1 找不到生成的可执行程序

我遇到的现象：

```text
bash: ./build/queue_demo: No such file or directory
```

我确认的原因：

CMake曾经把我的构建文件生成到：

```text
/home/zcb/build
```

而我运行命令时使用的是项目内部的：

```text
labs/blocking_queue/build
```

我的解决办法：

我把VS Code CMake Tools的构建目录统一配置为：

```text
${workspaceFolder}/labs/blocking_queue/build
```

我的总结：

以后运行程序前，我会确认CMake实际使用的源码目录和构建目录，不再只根据当前终端路径推测。

### 3.2 CMake可以编译，但VS Code仍然显示头文件错误

我遇到的现象：

我已经在CMake中添加头文件搜索目录，命令行编译成功，但VS Code仍然显示错误，代码补全也不能正常工作。

我确认的原因：

我确认编译器和VS Code代码分析器是两个不同的系统。CMake知道头文件路径，不代表VS Code的C/C++扩展已经读取了相同配置。

我的解决办法：

- 使用CMake Tools作为C/C++配置提供者；
- 开启`CMAKE_EXPORT_COMPILE_COMMANDS`；
- 确保VS Code打开的是仓库根目录；
- 重新执行CMake Configure。

我的总结：

我认识到“编译成功”和“编辑器没有红线”依赖不同的配置来源。

### 3.3 调试时出现undefined reference to main

我遇到的现象：

VS Code曾尝试单独编译我的`queue.c`：

```text
undefined reference to `main`
```

我确认的原因：

我使用了“编译当前活动文件”的调试配置。`queue.c`是队列库实现，不包含`main`函数，不能单独链接为可执行程序。

我的解决办法：

我改为通过CMake构建完整目标，并让调试器运行：

```text
build/queue_demo
```

我的总结：

以后调试多文件工程时，我会选择CMake目标，而不是随意单独编译当前源文件。

### 3.4 销毁队列时返回Device or resource busy

我遇到的现象：

```text
blocking_queue_destroy failed: Device or resource busy
```

我确认的原因：

我在销毁条件变量或互斥锁时，仍然可能有线程正在等待或访问队列。

我的解决办法：

我改为使用正确的退出顺序：

```text
关闭队列
→ 广播not_empty和not_full
→ 等待工作线程退出
→ pthread_join回收线程
→ 销毁条件变量和互斥锁
```

我的总结：

我把三者的职责总结为：`close`负责通知线程退出，`join`负责确认线程已经退出，`destroy`只能在最后执行。

### 3.5 最初使用错误码轮询满队列和空队列

我遇到的现象：

我的早期版本在队列满时返回`ENOSPC`，空时返回`EAGAIN`，线程通过循环反复重试。

我遇到的问题：

我确认这种轮询会浪费CPU，并且会让线程调度和退出逻辑更加复杂。

我的解决办法：

我加入了两个条件变量：

- `not_empty`：消费者等待数据；
- `not_full`：生产者等待空间。

我的总结：

我认识到条件变量必须和受互斥锁保护的条件表达式一起使用，并通过`while`重新检查条件。

### 3.6 测试文件超过一千行

我遇到的现象：

我最初把所有基础、阻塞、生命周期和并发测试集中在一个文件中，导致阅读和维护困难。

我的解决办法：

我按职责拆分为：

```text
test_queue_basic.c
test_queue_blocking.c
test_queue_lifecycle.c
test_queue_concurrent.c
test_helpers.c
test_helpers.h
```

我的总结：

我接受测试代码可能比功能代码更长，但不会再让一个文件承担所有测试职责。

### 3.7 两个消费者不能按完成顺序直接验证FIFO

我遇到的问题：

我发现两个消费者并发运行时，先取出数据的线程不一定先完成测试记录。因此我不能使用全局`received_count`直接判断下一个值。

我的解决办法：

我改为使用：

```c
seen_counts[value]++;
```

最后我检查`0～9999`中的每个整数是否恰好出现一次。

我使用单独的`result_mutex`保护测试统计数组，防止两个消费者同时修改造成数据竞争。

我的总结：

我认识到在多消费者环境中，“队列出队顺序”和“消费者完成处理顺序”不是同一个概念。

## 5. 我确认的当前实现限制

我的当前实现是学习版本，存在以下限制：

- 队列元素类型固定为`int`；
- 容量在编译期固定为4；
- 不支持带超时的`push`和`pop`；
- 不保证多个等待线程之间的公平调度；
- 尚未使用ThreadSanitizer检查数据竞争；
- 尚未保存网络数据包的内存所有权信息。

这些限制不影响我当前的多线程和条件变量学习目标。后续用于网络数据包任务时，我需要重新设计元素类型和数据所有权。

## 6. 我对后续项目复用方式的总结

在网络流量分析项目的实时多线程阶段，我可以复用本实验中的设计：

```text
抓包线程
    ↓
有界数据包队列
    ↓
协议解析线程
    ↓
解析结果队列
    ↓
输出或异常检测线程
```

我计划重点复用：

- 有界队列提供背压；
- 条件变量避免空转；
- `close`广播唤醒全部线程；
- `join`之后再销毁共享资源；
- 明确队列中任务的内存所有权。
