# 多线程流水线实验学习笔记

## 1. 生命周期与资源释放

### 1.1 什么是生命周期

生命周期表示一个对象或资源从“可以被安全使用”到“不能再被使用”的时间范围。

生命周期结束不一定等同于内存被`free`：

- 栈对象离开所属作用域后自动失效；
- `malloc`创建的堆对象一直有效，直到`free`或整个进程结束；
- 线程退出后仍需要由`pthread_join`回收可连接线程的相关资源；
- 互斥锁和条件变量需要通过对应的`destroy`函数结束生命周期；
- 队列的`close`表示业务上不再接收新对象，`destroy`才负责销毁同步资源。

### 1.2 `main`返回时堆内存会怎样

`malloc`得到的对象不会因为创建它的函数返回而自动释放，因此它可以在线程之间传递。

但是，`main`返回通常会结束整个进程，操作系统最终会回收该进程占用的地址空间。因此，更准确的说法是：

> 堆对象不受函数作用域控制，但仍然受整个进程生命周期限制。

程序仍然应该主动`free`不再使用的堆对象。长期运行的服务如果只等待进程退出时回收，内存会持续泄漏；主动释放也能让资源所有权清晰，并便于内存检查工具发现真正的问题。

### 1.3 为什么线程需要`pthread_join`

每个线程都有自己的执行状态和线程栈。线程函数返回表示它停止执行，但对于默认创建的可连接线程，主线程仍需调用`pthread_join`：

- 等待目标线程确实结束；
- 回收线程库保留的可连接线程资源；
- 保证目标线程写入的结果对等待线程可见；
- 确保后续销毁队列时，没有线程仍在访问队列。

`pthread_join`不能替代`free`，它回收的是线程相关资源，而不是线程曾经创建的业务对象。

### 1.4 队列为什么既要`close`又要`destroy`

`pointer_queue_close`和`pointer_queue_destroy`解决的是两个不同问题。

`close`属于运行协议：

- 把`closed`设置为`true`；
- 禁止新的`push`；
- 唤醒等待`not_empty`或`not_full`的线程；
- 让消费者在队列关闭且取空后收到`ECANCELED`并退出。

`destroy`属于资源回收：

- 销毁`pthread_cond_t`条件变量；
- 销毁`pthread_mutex_t`互斥锁；
- 结束队列内部同步对象的生命周期。

队列结构体本身位于`main`的栈中，因此不能对它调用`free`。但是它包含经过`pthread_mutex_init`和`pthread_cond_init`初始化的同步对象，所以仍然必须调用对应的销毁函数。

正确顺序是：

```text
通知队列关闭
    ↓
等待使用队列的线程退出（pthread_join）
    ↓
确认队列已经取空
    ↓
销毁队列内部同步资源（pointer_queue_destroy）
    ↓
main结束后，队列结构体占用的栈空间自动失效
```

不能先`destroy`再等待线程，因为其他线程可能仍在锁互斥锁或等待条件变量，这会造成未定义行为。

### 1.5 当前流水线中各种对象的生命周期

| 对象或资源 | 创建方式 | 生命周期如何结束 |
|---|---|---|
| `task`任务对象 | 生产者调用`malloc` | 工作线程处理完成后调用`free` |
| `result`结果对象 | 工作线程调用`malloc` | 输出线程输出完成后调用`free` |
| 线程上下文 | `main`栈中的局部变量 | `pthread_join`之后不再被线程使用，`main`返回时自动失效 |
| 两个队列结构体 | `main`栈中的局部变量 | 先`close`和`destroy`内部资源，`main`返回时栈空间自动失效 |
| 生产者、工作者、输出线程 | `pthread_create` | 线程函数返回，再由主线程`pthread_join` |

### 1.6 当前程序的完整退出顺序

```text
生产者完成任务创建
    ↓
生产者关闭task_queue
    ↓
工作线程取完已有任务并退出
    ↓
主线程join全部工作线程
    ↓
主线程关闭result_queue
    ↓
输出线程取完已有结果并退出
    ↓
主线程join输出线程
    ↓
主线程销毁两个队列
    ↓
main返回，进程结束
```

这个顺序的核心原则是：先停止资源的新使用者，再等待现有使用者退出，最后销毁资源。

## 2. 指针变量与指针指向的对象

### 2.1 声明指针不等于创建结构体对象

下面这行代码只创建一个能够保存地址的局部指针变量：

```c
pipeline_result_t *result;
```

它没有创建`pipeline_result_t`结构体，也没有分配堆内存。只有执行下面的代码时，才会在堆上创建一块能够保存`pipeline_result_t`的内存：

```c
result = malloc(sizeof(*result));
```

因此，工作线程和输出线程中名称相同的`result`是两个彼此独立的局部指针变量，但它们可以在不同时间保存同一个堆对象的地址。

### 2.2 结果对象如何在线程之间转移

```text
工作线程的局部result指针
    ↓ malloc
指向堆上的pipeline_result_t对象
    ↓ pointer_queue_push复制地址值
结果队列保存这个地址
    ↓ pointer_queue_pop取出地址值
输出线程的局部result指针保存同一个地址
    ↓ free(result)
堆上的pipeline_result_t对象被释放
```

`pointer_queue_push`复制的是地址值，不会复制结构体对象。入队成功后，工作线程把所有权交给队列，因此不能再释放或访问该对象；出队成功后，输出线程取得所有权，并在输出完成后调用`free`。

如果工作线程入队失败，所有权没有转移，仍然必须由工作线程调用`free(result)`。

## 3. 对象所有权

### 3.1 所有权是什么

所有权不是C语言提供的语法功能，而是项目约定的资源管理规则。某个组件拥有对象，表示它当前负责：

- 保证对象在使用期间仍然有效；
- 决定什么时候可以读取或修改对象；
- 对象不再需要时调用`free`；
- 在转交所有权后不再访问或释放对象。

所有权与“谁保存了地址”并不完全相同。多个位置可能暂时保存同一个地址，但项目必须明确只有谁负责最终释放，否则容易发生重复释放、释放后使用或内存泄漏。

### 3.2 当前流水线的所有权转移规则

```text
生产者malloc任务：生产者拥有任务
    ↓ push成功
task_queue暂管任务
    ↓ pop成功
工作线程拥有任务并在处理后free

工作线程malloc结果：工作线程拥有结果
    ↓ push成功
result_queue暂管结果
    ↓ pop成功
输出线程拥有结果并在输出后free
```

队列接口的约定是：

- `push`返回0：所有权已经转移，调用者不能再访问或`free`对象；
- `push`返回非0：所有权没有转移，调用者仍须负责`free`；
- `pop`返回0：消费者获得对象所有权；
- `pop`返回非0：消费者没有获得对象，不能使用输出指针。

队列本身只保存地址，不理解对象类型，也不会在正常销毁时自动释放对象。这里所说的“队列拥有”更准确地表示对象正在由队列暂管，等待所有权交给下一个消费者。异常清理时，主线程必须取出并释放队列中残留的对象。

## 4. CMake脚本与CSV验收测试

### 4.1 `.cmake`文件是什么

`.cmake`文件使用CMake自己的脚本语言。通过下面的命令可以让CMake以脚本模式执行它：

```bash
cmake -P script.cmake
```

脚本模式不会编译C代码，也不会生成Makefile或Ninja构建规则，而是按照顺序执行`file`、`list`、`math`、`execute_process`和`message`等CMake命令。

`CMakeLists.txt`主要负责描述如何配置、编译、链接和注册测试；独立的`.cmake`脚本适合执行构建过程之外的辅助工作，例如启动程序、准备测试文件和检查程序生成的文件。

### 4.2 为什么CSV验收需要脚本

以前的指针队列单元测试把数据直接传给C函数，并在测试程序内部判断返回值，因此测试可执行程序本身返回0或非0就足以表示通过或失败。

当前需要验证的是完整系统行为：

```text
启动五线程流水线程序
    ↓
等待程序生成CSV
    ↓
读取CSV文件
    ↓
验证表头、行数和每个任务的计算结果
```

CTest默认只能根据被执行命令的退出状态判断成功或失败。流水线程序返回0能够证明运行过程没有报告错误，但不能单独证明CSV的内容完全正确。因此使用`verify_pipeline_csv.cmake`充当测试驱动器和结果检查器。

### 4.3 CTest、CMake脚本和被测程序的关系

```text
CTest
  ↓ 执行cmake -P
verify_pipeline_csv.cmake
  ↓ execute_process
thread_pipeline_demo
  ↓
pipeline_acceptance.csv
  ↑ file(STRINGS)读取并验证
verify_pipeline_csv.cmake
  ↓ 返回成功或FATAL_ERROR
CTest
```

这种测试属于集成测试或验收测试，因为它验证线程、队列、计算、文件输出等多个组件组合后的最终行为。

### 4.4 为什么选择CMake脚本

- 项目已经依赖CMake，无需额外安装测试语言或框架；
- 能被CTest直接调用；
- Linux、Windows等使用CMake的平台都可以运行；
- 当前CSV格式简单，CMake提供的文件和字符串操作已经足够。

如果以后需要解析复杂CSV、大量数据或执行统计分析，CMake脚本会变得难以维护，此时更适合使用Python测试脚本或专门的测试工具。
