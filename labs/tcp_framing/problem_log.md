# TCP 定长头与变长载荷实验问题记录

本文记录我在TCP消息分帧实验中实际遇到的问题、排查过程和经验。

## 1. 实验目标

本实验用于学习和验证以下 Linux 网络编程知识：

- IPv4 TCP 服务器的创建、绑定、监听和连接接受；
- IPv4 TCP 客户端的创建和主动连接；
- TCP 是连续字节流，不保留应用层消息边界；
- `send` 和 `recv` 可能只处理请求数据的一部分；
- 固定长度消息头与变长载荷的组合；
- 主机字节序与网络字节序转换；
- 对端提前关闭、非法消息和异常长度处理；
- 单元测试与真实回环 TCP 集成测试。

## 2. 最终实现行为

消息在线格式固定为：

```text
0       4       5       6       8               12
+-------+-------+-------+-------+----------------+
| magic |version| type  |reserved| payload_length|
+-------+-------+-------+-------+----------------+
|                  payload ...                   |
+------------------------------------------------+
```

主要模块职责：

- `message_protocol`：消息头编码、解码和字段校验；
- `stream_io`：循环执行 `send` 或 `recv`，直到完成指定长度；
- `message_io`：先收发固定消息头，再根据长度收发载荷；
- `tcp_server`：创建监听 Socket 并接受客户端连接；
- `tcp_client`：创建 Socket 并主动连接服务器；
- `tcp_framing_acceptance_tests`：通过真实 IPv4 回环连接完成最终验收。

## 3. 遇到的问题与工程难点

### 3.1 TCP 不保留应用层消息边界

问题：

一次 `send` 不保证对应接收端的一次 `recv`。一条消息可能被拆成多次接收，多条消息也可能连续出现在同一段字节流中。因此不能把一次 `recv` 返回的数据直接当作一条完整消息。

解决办法：

- 使用固定 12 字节消息头；
- 在消息头中编码 `payload_length`；
- 先通过 `recv_exact`读取完整消息头；
- 解码并校验长度后，再通过 `recv_exact`读取对应载荷。

验证：

- 人为按照 1、2、3、5 字节的小块发送消息头和载荷；
- 连续发送多条不同类型、不同长度的消息后再逐条接收；
- 验证接收端仍能恢复每条消息的正确边界。

经验：

TCP 只保证字节的可靠、有序传输，消息边界必须由应用层协议定义。

### 3.2 `send` 和 `recv` 可能只处理部分数据

问题：

即使缓冲区长度为 100 字节，`send` 或 `recv` 的一次调用也可能只处理其中一部分。直接假设返回值等于请求长度，会造成截断消息或错误解析。

解决办法：

- `send_all`累计已经发送的字节数，直到全部完成；
- `recv_exact`累计已经接收的字节数，直到满足指定长度；
- 系统调用被信号中断并返回 `EINTR` 时重新尝试；
- 对端提前关闭且数据不足时返回 `ECONNRESET`。

经验：

所有流式 I/O 接口都必须检查实际返回长度，不能只检查成功或失败。

### 3.3 不能直接发送内存中的消息头结构体

问题：

直接发送 `message_header_t` 会依赖编译器结构体填充、枚举宽度、CPU 字节序和内存对齐。在 x86_64 上看似可用的数据，在 ARM 或其他编译器上可能产生不同格式。

解决办法：

- 明确定义 12 字节线上格式和每个字段的偏移；
- 使用 `uint8_t`字节缓冲区保存编码结果；
- 使用 `htonl`、`htons`、`ntohl`和`ntohs`转换多字节整数；
- 使用 `memcpy`访问多字节字段，避免未对齐访问和别名规则问题；
- 不使用 `sizeof(message_header_t)`作为协议头长度。

经验：

内存结构体是本机数据模型，网络协议是跨平台字节格式，两者必须显式转换。

### 3.4 失败时不能发布部分有效的输出对象

问题：

如果消息头已经解码，但载荷随后接收失败，调用者可能获得一个看似有效的消息头，并误认为完整消息已经到达。

解决办法：

`message_receive`使用局部变量保存解码后的消息头，只有消息头和全部载荷都成功接收后，才执行：

```c
*header = decoded_header;
```

客户端连接函数也采用相同原则，只有 `socket`、地址转换和 `connect`全部成功后，才把文件描述符写入输出参数。

经验：

资源创建或复合操作应当在全部成功后再向调用者发布结果，使接口保持明确不变量。

### 3.5 测试代码出现未使用变量警告

现象：

```text
warning: unused variable 'header' [-Wunused-variable]
```

原因：

消息参数测试重构后不再使用局部变量 `header`，但变量定义仍然保留。

解决办法：

删除无效变量，并保持测试目标启用：

```text
-Wall -Wextra -Wpedantic
```

经验：

测试代码也需要保持零编译警告。警告经常能够发现重构残留、错误变量或没有真正执行的验证逻辑。

### 3.6 自动化集成测试不能依赖固定端口

风险：

如果测试固定使用 9000 端口，而该端口正被演示服务器或其他程序占用，测试会因为环境冲突失败，而不是因为被测功能错误。

解决办法：

- 服务器绑定端口 0，让 Linux 自动选择空闲端口；
- 使用 `getsockname`查询实际绑定端口；
- 客户端连接查询得到的端口；
- 每项验收测试建立独立连接并及时关闭全部文件描述符。

经验：

自动化测试应尽量自行创建隔离资源，避免依赖容易冲突的外部环境状态。

## 4. 最终验证结果

单元和模块测试：

```text
message_unit_tests
stream_io_unit_tests
message_io_unit_tests
```

真实 IPv4 TCP 最终验收：

```text
[PASS] send 1000 messages
[PASS] fragmented message
[PASS] multiple consecutive messages
[PASS] peer closes early
All TCP framing acceptance tests passed.
```

CTest结果：

```text
4/4 tests passed
```

验收覆盖：

- 连续收发 1000 条带序号消息；
- 消息头和载荷被人为分段发送；
- 多条消息连续发送后边界保持正确；
- 零载荷 PING 与文本消息连续出现；
- 对端在载荷未完整发送时关闭；
- 接收失败后输出消息头保持原值；
- 全部监听Socket和已连接Socket完成关闭。

## 5. 当前实现限制

当前实现是学习阶段的最小协议，仍有以下限制：

- 只支持 IPv4，不支持 IPv6；
- 演示服务器只接受一个客户端和一条消息；
- 没有连接、读取和写入超时；
- 没有校验和、加密、身份认证与权限控制；
- 单条载荷固定限制为 4096 字节；
- 不支持协议协商、心跳超时和断线重连；
- `connection_close`目前位于 `tcp_server`模块，后续可提取为通用Socket资源模块。

这些限制不会阻碍A2热身目标，但如果把协议用于后续告警上传或控制接口，需要根据实际需求逐项完善。
